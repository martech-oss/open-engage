# SOLID・整合性・性能改善の実装結果

## 変更内容

1. Queue送信を100件・256,000 bytes以下の単位に分割。UTF-8 JSONとメタデータ分を計算し、成功した単位のleaseを保持する。Cronはドメイン別タスクを実行し、独立した後続タスクを実行した後で例外を報告する。
2. スコア実行時の200件制限を除去。加点を50ルールずつ原子的に適用し、イベント×ルールの一意性で再試行の二重加点を防ぐ。全ルールを処理してから後続処理へ進む。管理画面は50件既定・100件上限のカーソルページに変更し、カードの集計値は全件に対するSQL集計を使う。
3. ダッシュボードを専用Repositoryに変更。オートメーション全件集計・SQL上位6件、必要な推移・合計だけを取得する。配信はメールのaccepted/delivered/failedを対象とし、現在状態または過去のdeliveredイベントで到達を判定する。この条件はメールレポートと共通化した。14日・30日・ワークスペースタイムゾーンを維持する。
4. 複製の一覧・進捗を軽量DTOと専用読み取りRepositoryへ分離。previewをSQLで除外してページ取得し、表示用の取得ではスナップショット本文を転送しない。ジョブ処理と最終確定も分離し、種別ごとの変換・書き込み・順序を型で網羅する。最終確定は参照・leaseの検証を含む原子的なD1 batchを維持する。
5. CSV取込は入力・要求キー・ジョブ・行結果・leaseを永続化してから受付結果を返す。専用Queueで25行ずつ順番に実行し、成功済み行は再適用しない。公開定義は処理単位で再利用し、公開版の更新と競合した場合だけ再取得する。行結果と参加者変更は同一batchで確定する。完了監査も一度だけ原子的に記録する。

## 契約

- `scoring.listRules` / `listCriteria`: `{ cursor?, limit? }` → `{ items, total, nextCursor?, summary }`。summaryは表示中ページではなく全件の集計。
- `projects.cloneList`: 一覧用ページ。`cloneProgress`: 一覧と同じ軽量進捗。previewや参照一覧が必要な場面は`cloneGet`を使用する。
- `projects.memberImport`: `{ id, csv, idempotencyKey }` → `{ jobId, status, total, processed, rows }`。初回受付のrowsは空。`memberImportGet({ id, jobId })`で状態と行別結果を取得する。同じキーの異なるCSVは409。
- Client、共有oRPC契約、SDK、既存のMCPツールを同じ差分で更新した。SDKは共有契約から型を導出する。MCPには元々スコア設定ツールがないため、ページングだけを理由に新しいスコア操作ツールは追加していない。
- 過去のスコアの自動再計算・遡及補正は含まない。

## ローカル比較

同じ件数・内容のfixtureでD1呼び出しを観測した。時間はローカルの単発計測で、ネットワーク・Queue待ち・本番の競合を含まない。応答時間の保証やp95改善率を意味しない。

| 対象                                                              |           変更前 SQL | 変更後 SQL |        D1返却データ量 前→後 | ローカル時間 前→後 |
| ----------------------------------------------------------------- | -------------------: | ---------: | --------------------------: | -----------------: |
| Dashboard（201下書き＋古い有効Automation）                        |                   20 |         11 |        23,374 → 2,282 bytes |   21–25 → 16–17 ms |
| 複製一覧（25実行履歴＋新しい20preview、source/target合計約100KB） |                   41 |          1 |     2,016,661 → 3,943 bytes |          14 → 3 ms |
| 複製詳細（同fixture）                                             |                    2 |          2 |         100,789 → 495 bytes |           1 → 2 ms |
| 複製進捗（従来は詳細取得）                                        |                    2 |          1 |         100,789 → 189 bytes |           1 → 1 ms |
| CSV全体（同一Contactの1,000行）                                   |               11,007 |      6,214 | 2,703,868 → 2,500,399 bytes |   2,161 → 1,083 ms |
| CSVのHTTP受付部分                                                 | 全行処理完了まで待機 |          8 |                77,379 bytes |               4 ms |

CSVのD1往復は11,002→4,208回。変更後の全体値は受付と40回のジョブ実行の合計で、Queue待機時間は除く。行ごとの再開情報の書き込みは増えるが、公開定義と施策の繰り返し取得を減らしている。

返却データ量はD1の結果オブジェクトをUTF-8 JSONにしたバイト数（メタデータを含む）であり、ブラウザーへの転送量ではない。`raw()`で返却メタデータが省略されるため、部分的な`rows_read`値を総スキャン行数の比較には使っていない。Dashboardの変更前は一部の設定を取りこぼしており、変更後は全件を正しく集計する。

## 展開

1. DB migration `0025_program_member_import_jobs.sql`を先に適用する。既存データを書き換えない追加テーブルの移行。
2. `<project-name>-program-member-import` Queueを作り、`PROGRAM_MEMBER_IMPORT_QUEUE`を設定する。consumerは`max_batch_size=1`。新規導入CLIにも作成処理を追加した。
3. 新Serverを配置し、対応するClient/SDK/MCP利用側を切り替える。今回は移行後の契約を実装しているため、旧Clientを新Serverに混在させない。段階公開では旧Serverと旧Clientの組を保持し、新しい組を検証してから利用側を移行する。別originとWorker bindingで旧版・新版を隔離し、各Clientが同じ版のAPIに接続するようにする。既存ブラウザーの再読み込みも切替確認に含める。旧SDK/API利用側も一覧の配列返却・CSVの即時完了への依存を更新し、対応する新版Serverへ接続先を切り替える。
4. 新しい組への移行確認後、旧リリースを廃止する。ロールバック時もServerとClientの組を揃え、新テーブルは保持する。ただし旧ServerにはCSV専用consumer・復旧処理がないため、先に新規取込受付を止めてpending/runningジョブを完了させるか、全ジョブ完了まで新版のconsumerとCronを維持する。専用Queueも全ジョブ完了まで保持する。受付済みジョブが残る状態でこれらを旧版に置き換えない。

この作業では本番DBへの適用、Queue作成、デプロイは行っていない。
