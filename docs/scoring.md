# スコアの上限と減衰

ルール編集の「減衰日数」「コンタクトごとの加点上限」は任意です。空欄は従来どおり減衰・上限なしです。正の加点ルールにのみ指定できます。減衰日数は1〜3650、加点上限は1〜1,000,000の整数です。負の減点やタグだけのルールには設定できません。

減衰はイベント発生日時から24時間の整数日数で計算し、残り点数を切り捨てます。20点・10日なら5日後は10点、10日後は0点です。遅れて識別・処理されたイベントも元の日時で計算します。上限で一部だけ認められた加点は、その部分を元のイベント日時から減衰します。タグは減衰で外しません。

上限はそのコンタクトについて、そのルールが現在残している加点合計に適用します。上限に達したイベントも処理済みになり、後から点数が減っても再送で加点されません。上限の空きは定期減衰が保存済み点数に反映された時点で戻ります。ルール編集で上限を下げても既存の加点は取り消さず、以降のイベントを制限します。

新しい設定は以後処理されるイベントに適用します。Migration前の履歴を再計算せず、既存の総点を維持します。導入後の正の行動加点は独立した寄与として記録し、当時のカテゴリ・減衰日数を保持します。ルールやカテゴリを編集・アーカイブしても元の寄与は減衰し続けます。元の行動履歴が保持期限でR2へアーカイブされても減衰を継続します。生のイベントを物理削除すると既存のスコア履歴にも影響するため、独自の削除処理を追加する場合は日次スコア補正との整合性を別途確認してください。手動・Automationの点数調整には減衰差分だけを重ねます。

通常Cronは最大20件ずつ寄与を処理し、処理対象が残っていれば既存のJOBS_QUEUEへ継続処理を送ります。Queueも1回最大20件ずつ処理し、次のCronを待たず残りを継続します。継続中は起点の判定日時を固定し、翌日以降に期限が来る寄与まで追い続けません。Queue送信に失敗しても未処理の寄与はDBに残り、次のCronで再取得します。実際の処理能力はQueueの混雑、D1のクエリ量・実行制限に依存します。

アーカイブ済みコンタクトは更新せず、復元後は経過日数で再計算します。各減衰の総点・カテゴリ点・スコア履歴・`score_changed`イベントと再評価用outboxは1トランザクションで保存します。並行Cron・Queueの再試行は比較更新で重複減点しません。既存のイベント処理でグレード、Automationのイベント判定・登録、セグメント再評価を実行し、途中失敗はoutboxから再試行します。減衰による内部の`score_changed`イベントは最終活動日時に含めず、休眠判定・再参加の起点を更新しません。

Migration `0026_scoring_limits_decay.sql` はnullable設定列と空の寄与テーブル・索引を追加します。適用前にバックアップを取り、[既存のD1 migration手順](../README.md#3-d1-migration)に従い、開発環境では `pnpm db:migrate:local`、対象リモート環境では設定先DBを確認して `pnpm db:migrate:remote` を実行してから新しいサーバーを使用します。この変更の実装・検証では実際の開発DBやリモートDBへのmigration適用、デプロイは実行していません。
