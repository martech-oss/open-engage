# Apollo.io 機能ギャップ分析

Apollo.ioは、B2Bの人物・企業データベースを中心に、見込み客の探索、連絡先の取得、シーケンスによるアプローチ、電話、会議、商談までを営業担当者向けに一体化した製品です。OpenEngageは、**フォーム獲得 → 動的セグメント → スコア → 営業引き渡し → 受注・施策成果測定**を担うマーケティングオートメーションです。重なる領域はContact・Company・Deal・Task、フォーム、訪問者計測、スコア、ワークフロー、AI、API/MCPです。この資料では、Apolloとの差から、OpenEngageに追加すべき機能を洗い出します。

- 調査日：**2026-09-30**。
- 対象：OpenEngage `v0.1.0`、コミット **`47bc96329e222e1dad31873f964bc54c372d7efa`**。調査開始時の作業ツリーに変更なし。
- 比較：Apollo.ioのFree / Basic / Professional / Organization。Apolloの公式ページ本文はこの調査環境から取得できなかったため、公式ドメインに限定した検索結果の要約を根拠にした（[6. 検証と限界](#6-検証と限界)）。
- 成果物：機能差と、追加すべき機能の優先度。アプリケーション、API、DBの変更は含まない。

## 1. 結論

1. **Apolloの中心にあるデータ資産は追わない。** 2億件超の人物データ、メール・電話番号の取得、Bomboraのインテント、求人・資金調達データ、IPから企業を特定するデータは、コードを追加しても得られない。OpenEngageでは、外部データを**受け入れて活用する側**の機能を整える。
2. **最大の差は、営業担当者が毎日使う実行面にある。** Apolloのシーケンスは、自動メール、電話、LinkedIn、ToDoを1本の手順にまとめ、返信があれば自動で終了する。OpenEngageにも、Automation、署名付きReply-Toによる返信検知、Contact単位のタスク、担当者の順番割り当てがある。しかし、これらは互いにつながっていない。この統合は、現在のメール送信方針を変えずに実現できる。
3. **データの受け皿が最初の課題。** Contactには役職・部署・タイムゾーン等の標準項目がない。CompanyはAPI上、名前とドメインしか扱えない。カスタム項目定義の管理UIは、HubSpot比較（2026-09-09）で「高」とした後も未着手である。会社調査Agentが11項目を提案しても、保存できるのは2項目だけ。Apollo型の補完、AI Research、会社単位の優先度付けは、どれもこの受け皿に依存する。
4. **会社単位の優先度付けは、外部データなしで始められる。** Apolloの訪問企業識別やインテントは外部データに依存する。一方、OpenEngageは特定済みContactの閲覧・フォーム・メール反応・スコアを保存しており、会社詳細には所属Contactごとのスコアも出る。これを会社単位に集計すれば、「今動いている会社」を自前のデータで示せる。
5. **担当者メールボックスからの1:1送信は、方針を決めてから着手する。** これはApolloの中核機能である。しかしOpenEngageはCloudflare Email ServiceのTransactional送信に限定しており、差出人もWorkspace共通である。採否と同意要件の方針を決める前に実装を始めない。

## 2. 対象・判定方法

### 除外と製品境界

| 区分                | この調査での扱い                                                                                                                                                                                                                              |

| 電話・録音          | 通信事業者との契約や録音の同意が必要になる発信、録音、会話分析は、差分を記録したうえで見送り。通話結果の記録は対象とする。                                                                                                                    |

**実装済み**は、行に記載した能力を確認したという意味であり、Apolloとの完全互換、同じ操作感、同じ処理規模を意味しない。**部分実装**は、利用できる範囲と不足を併記する。**未実装**は、関連する型・契約・実行処理・UIを調べても該当機能を確認できなかったもの。**対象外**は、上記の方針により比較から外したもの。

表中の **F / B / P / O** は、Free / Basic / Professional / Organization を指す。プラン条件は、公式ページの検索結果の要約から読み取った目安である。原文を読んでいないため、契約判断にはリンク先で確認すること。`E01`などは[コード・テスト根拠](#5-コードテスト根拠)への参照。優先度の「—」は、その行について新規開発を推奨しないことを表す。

### 4.2 方針判断が必要な項目

**担当者メールボックスからの1:1送信（S03）** はApolloの中核機能だが、OpenEngageの現行方針（Cloudflare Email ServiceのTransactional専用、Workspace共通の差出人、Marketingの停止）とは別の設計になる。採否の前に、次の点を決める必要がある。

- **用途の定義。** Transactional・Marketingとは別の「営業1:1」用途を型に追加するか。送信直前の同意・抑止・頻度判定を、どの用途と共有するか。
- **同意と法令。** 面識のない相手への営業メールは、日本の特定電子メール法やGDPR等の同意要件との整合を確認する必要がある。Apolloにも、GDPRモードや削除依頼の管理がある（[GDPR][a-gdpr]・[削除依頼][a-removal]）。X06を先行させる。
- **送信経路。** 採用する場合は、Gmail API・Microsoft GraphをHTTPSで使い、担当者ごとのOAuth、1日の上限、返信の同期を持たせるのが現実的。ウォームアップ網やドメイン販売は対象外のまま。
- **不採用の場合の代替。** 高3.のタスクに「メールクライアントで開く」導線を置き、送信記録はBCC用の受信アドレスで取り込む。既存のEmail Routingの受信処理を拡張する必要がある。

### 4.3 優先度：中

- **外部データプロバイダーの接続（C03/C04/I03）**：利用者自身のAPIキーで、Apollo APIを含む補完サービスを順番に呼び出す。結果は出典付きで保存し、実行量の上限（X07）の対象にする。Apolloとの併用時は最も効果が大きい。
- **Webhookのイベント配信（W02）**：保存済みの`eventTypes`に従い、Contact作成、フォーム送信、ライフサイクル到達、商談の更新等を配信する。Apolloのワークフローや外部の自動化ツールとつなぐ最小の経路になる。負担は小〜中。
- **MCPの対象拡大（W03）**：Deal、タスク、Companyの操作をMCP Toolとして公開する。既存のoRPC契約からの登録処理を再利用できる。
- **消去依頼とDo Not Contact（X06）**：個人情報の消去と、再取り込みを防ぐためのハッシュ保持、手動の抑止登録。外部データを取り込む前に必要。
- **重複の検出・統合（C08）**：人が候補を確認し、プレビュー付きで統合するところから始める。履歴、商談、施策参加、スコア、同意の引き継ぎ規則が主な負担。
- **メールアドレスの検証（C05）**：構文、MX、使い捨て・ロールアドレスの判定。CSV取り込み時とフォーム送信時に使う。
- **受信者タイムゾーンでの送信（S04）**、**通話結果の記録（S08の一部）**、**保存ビューと新規一致の通知（D04）**、**カスタムレポート（R03）**：それぞれ高1.・高3.の後に追加する。

### 4.4 優先度：低・見送り

自社のB2Bデータベース、連絡先の取得（D03/C01）、インテント・求人・資金調達のシグナル（D06）、類似企業の探索（D05）は、データ資産の問題であり見送る。IP→企業の識別（I01）とフォームの外部補完（I03）は、外部プロバイダーとプライバシー評価が前提。ダイヤラー、録音、会話分析（S08/T04）、ブラウザ拡張とLinkedIn連携（S09）、ウォームアップとドメイン販売（S05）、予測AIスコア、SSO/SCIM（X05）も見送る。Cloudflare上にアプリを置けても、外部データ、通信事業者、モデルの費用まで不要になるわけではない。

### 4.5 Apolloと併用する場合の構成

Apolloを営業のデータ調達とアウトバウンドに、OpenEngageをインバウンドの獲得・育成・スコア・成果測定に使い分ける場合は、次の3点で連携するのが最小構成である。

| 方向                | 経路                                                                         | 必要な追加          |
| ------------------- | ---------------------------------------------------------------------------- | ------------------- |
| Apollo → OpenEngage | ApolloのワークフローのSend Webhookから、OpenEngageのイベント受信APIへ送る。  | なし（既存APIで可） |
| OpenEngage → Apollo | MQL到達や閾値超えのイベントをWebhookで配信し、Apolloのシーケンスへ登録する。 | W02のイベント配信   |
| 補完                | 利用者のApollo APIキーで、Contact/Companyを補完する。                        | C04・X07・D01/D02   |

### 4.6 営業プロセスで見る優先順位

| 段階           | Apolloの主な機能                              | OpenEngageで現在できること                               | 次に不足すること                                  |
| -------------- | --------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------- |
| ターゲット定義 | 外部データベースの検索、Persona、インテント   | 自社データの動的セグメント、自然言語からのセグメント生成 | 標準項目とカスタム項目の運用（高1.）              |
| データ補完     | 連絡先の取得、ウォーターフォール、AI Research | 会社調査の提案（保存は名前とドメインだけ）               | 提案の保存、一括実行、AI Research（高2.）         |
| 優先度付け     | 訪問企業、Signals、Scores                     | Contact単位のスコア、グレード、減衰                      | 会社単位のエンゲージメント（高4.）                |
| アプローチ     | シーケンス、メールボックス、ダイヤラー        | 自動メール、返信検知、営業引き渡しとタスク               | タスク付きシーケンスと自動終了（高3.）、S03の方針 |
